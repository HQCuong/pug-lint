# fix guard

会破坏模板的自动修复，还不如没有自动修复。Pug 很容易出这种问题：缩进就是结构，
只移动一行而不带上它的子节点，树就变了。所以每个涉及 Pug 模板的修复，在 ESLint 应用之前都会经过检查。

## 检查什么 {#what-is-checked}

对每个 Pug 模板，只有在修复之后模板仍然能解析、且结构没有变化时，才会应用该修复：

- 标签及其嵌套关系；
- 每个标签的 class 和 id 集合以及属性数量（所以 `p(class="a b")` 和 `p.a.b` 相等，但丢失一个 class 就不相等）；
- 文本和插值的形态；
- Pug 会编译的每一段 JavaScript（不带引号的属性值和 `${}` 属性值、`&attributes`、
  mixin 参数、代码、控制语句头、`#{}`），缩进除外。

解析器会报告 Pug 本身会拒绝的情况（例如 Tab 和空格混用，或重复的属性），
所以会引入这些问题的修复同样会被丢弃。

## 修复如何应用 {#how-fixes-are-applied}

1. 每个修复都会单独验证。
2. 通过验证的修复会再作为 ESLint 将要应用的组合整体验证一次。
3. 未通过的修复会被丢弃，它对应的问题仍然会被报告，你可以手动修复。

这涵盖所有会修复 `.vue` 文件的 rule，包括 `vue/*` rules 和第三方 rules。
当模板存在 Pug 语法错误时，不会在其中应用任何修复。

## 开销 {#cost}

对每个不同的修复，guard 都要重新解析一遍模板，所以开销随修复数量乘以模板大小增长。普通模板只需几毫秒；
一个格式完全混乱的 3000 行模板可能需要几秒。只有当模板存在待修复的问题时才会产生这个开销。

## 部分修复集 {#partial-fix-sets}

guard 验证的是通过验证的修复的完整集合。如果 ESLint 只应用其中一部分
（`--fix-type`，或 Node.js API 中自定义的 `fix` 谓词），那么这个子集作为一个整体并没有被验证过。
