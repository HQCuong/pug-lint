# fix ガード

テンプレートを壊す autofix は、autofix がないよりも悪い結果になります。Pug ではそれが起きやすく、インデントが構造そのものなので、子を残したまま 1 行だけ動かすと木構造が変わります。そのため、Pug テンプレートに触れるすべての fix は、ESLint が適用する前に検証されます。

## 何を検証するか {#what-is-checked}

Pug テンプレートごとに、fix は適用後もテンプレートがパースでき、かつ構造が変わらない場合にだけ適用されます。比較する対象は次のとおりです。

- タグとそのネスト。
- 各タグのクラスと id の集合、および属性の数（そのため `p(class="a b")` と `p.a.b` は同じとみなされますが、クラスが失われると別物になります）。
- テキストと補間の形。
- Pug がコンパイルするすべての JavaScript（クォートなしの属性値や `${}` の属性値、`&attributes`、mixin の引数、コード、制御構文のヘッド、`#{}`）。インデントの違いは無視します。

パーサーは Pug 自身が拒否するもの（たとえばタブとスペースの混在や、属性の重複）も報告します。そのため、それらを持ち込む fix も破棄されます。

## fix の適用方法 {#how-fixes-are-applied}

1. 各 fix を単独で検証します。
2. 残った fix を、ESLint が適用する組み合わせとして再度検証します。
3. 検証に失敗した fix は破棄されますが、その問題は引き続き報告されるので、手作業で直せます。

これは `.vue` ファイルを fix するすべての rule に適用されます。`vue/*` rule もサードパーティの rule も含みます。テンプレートに Pug の構文エラーがある間は、その中で fix は一切適用されません。

## コスト {#cost}

ガードは、異なる fix ごとにテンプレートを再度パースします。そのため、コストは fix の数とテンプレートのサイズの積に比例して増えます。通常のテンプレートならミリ秒で終わりますが、整形がまったくされていない 3000 行のテンプレートでは数秒かかることがあります。コストが発生するのは、テンプレートに fix すべき問題があるときだけです。

## 一部だけの fix セット {#partial-fix-sets}

ガードは、残ったすべての fix を 1 つの組として検証します。ESLint がその一部だけを適用する場合（`--fix-type` や、Node.js API のカスタム `fix` predicate）、その部分集合は組としては検証されていません。
